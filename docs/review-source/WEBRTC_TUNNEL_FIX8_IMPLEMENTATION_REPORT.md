### P0-006 — exact reset, corruption-tolerant, attempted-stage rollback — commits `0621d75`, `0dbefda`
`TransactionalResetCoordinator` had not been brought up to the attempted-before-apply/exact-snapshot standard the other three coordinators (Setup, ForwardConfiguration, and P0-003/004/005's primitives) already met. Four real defects found and fixed:
- **Corrupt setup JSON blocked reset entirely** (HIGH-5): `captureSnapshot()` called `configRepository.loadSetupInputResult().getOrThrow()` before every reset, so a corrupt `setup_input.json` — the exact state a user needs reset to repair — permanently blocked it. Capture is now raw bytes only (`captureSetupInputFileSnapshot`, already exact/injectable), no parsing.
- **Config was captured lossily**: `configContents` (a UTF-8 `String`) was converted `.toByteArray()`, corrupting non-UTF-8 bytes on any snapshot/restore cycle. Fixed via a new `ConfigRepository.captureConfigSnapshotForReset` property (raw bytes, `captureExactFileSnapshot`) — and the restore side had the *same* bug (a `String(bytes, UTF_8)`-converted `writeConfigAtomically` call), found and fixed in the follow-up commit (`0dbefda`) once a dedicated non-UTF-8 test caught it; restore now delegates to the existing `ConfigRepository.restoreConfigSnapshot` byte-exact primitive.
- **Snapshot failure was unconditionally reported as `ResetStage.Config`** regardless of which component's capture actually failed. `SnapshotCaptureException` now carries the real stage (`Config`/`SetupInput`/`Forwards`).
- **Attempted-vs-applied ordering bug** (CRITICAL-2, the same class fixed for every other coordinator this cycle): stages were added to the rolled-back set only *after* their own apply succeeded, so a stage that changed its destination and only then reported failure would never be rolled back. Fixed identically to P0-003/004/005: `attempted` gains a stage before its apply runs, `applied` (only genuine successes) drives each stage's `stageWasApplied` restore parameter.
